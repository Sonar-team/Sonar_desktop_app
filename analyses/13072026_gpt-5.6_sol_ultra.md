## Verdict

  SONAR n’est plus une bêta fragile : le cœur Rust, la compilation et la supply chain sont déjà sérieux. En revanche, je le classerais encore comme une bêta avancée / RC technique, pas comme un produit professionnel terminé.

  Le blocage principal n’est pas le nombre de fonctionnalités. C’est la chaîne de confiance :

  > capture → décodage → agrégation → visualisation → sauvegarde → preuve exportée

  Aujourd’hui, SONAR ne garantit pas encore qu’aucun paquet ou flux n’a été silencieusement ignoré, écrasé ou fusionné à tort.

  ## Les six blocages avant une version « Pro »

  ### 1. Garantir qu’aucune donnée ne disparaît silencieusement

  C’est le P0 absolu.

  - Le type de lien PCAP/DLT n’est pas vérifié. Les données sont envoyées directement au parseur Ethernet dans sonar-rust/crates/sonar-flows-core/src/pcap.rs:55. Un PCAP Linux cooked, RAW, loopback, radiotap ou multi-interface peut donc produire une
    matrice vide ou incorrecte sans explication.

  - L’import desktop ignore silencieusement les erreurs de décodage dans src-tauri/src/commandes/import/pcap.rs:159, et l’événement final n’expose pas parse_errors src-tauri/src/commandes/import/pcap.rs:379.
  - Une course permet à une capture de démarrer pendant un import, puis à l’import d’écraser les données capturées lors du commit. L’état ne réserve pas de phase Importing dans src-tauri/src/state/capture/mod.rs:90.
  - L’arrêt d’une capture peut abandonner un paquet tardif à cause d’un drainage limité à 250 ms dans src-tauri/src/state/capture/capture_handle/threads/processing.rs:363.
  - Lorsque la limite de 250 000 flux est atteinte, le canal n’est pas drainé avant l’arrêt src-tauri/src/state/capture/capture_handle/threads/processing.rs:648.
  - Le graphe identifie les nœuds principalement par IP ou MAC dans sonar-rust/crates/sonar-flows-core/src/graph.rs:14. Deux équipements ayant la même IP sur des VLAN ou sites différents peuvent être fusionnés.

  Il faut produire pour chaque session un bilan vérifiable :

  paquets lus
  = décodés
  + DLT non supportés
  + paquets tronqués
  + erreurs de lecture
  + pertes interface/noyau
  + pertes application

  Aucune catégorie ne doit être silencieuse.

  ### 2. Introduire de vrais projets d’analyse persistants

  L’état métier reste essentiellement en mémoire. La fermeture appelle directement exit(0) dans src/utils/appExit.ts:19, sans sauvegarde transactionnelle ni récupération après crash.

  Une version pro doit avoir :

  - un format de projet versionné ;
  - autosave et checkpoints ;
  - récupération après crash ;
  - état « modifications non sauvegardées » ;
  - arrêt gracieux : arrêter le producteur, drainer, joindre les threads, sauvegarder ;
  - provenance des PCAP : SHA-256, taille, DLT, interface, filtre et dates ;
  - versions de SONAR, du parseur et du schéma ;
  - manifest final signé avec les compteurs de pertes et d’erreurs.

  C’est ce qui transforme une visualisation en preuve d’audit reproductible.

  ### 3. Terminer le parcours produit principal

  La matrice de flux, pourtant centrale dans la proposition de valeur, n’est actuellement plus affichée : la vue active rend seulement le graphe et les dernières trames dans src/views/analyseView.vue:31.

  Le composant src/components/AnalyseView/Matrice.vue:117 est déconnecté, limite son rafraîchissement et appelle une commande reset inexistante.

  Il faudrait livrer un parcours unique et cohérent :

  1. Créer ou ouvrir un projet.
  2. Capturer ou importer.
  3. Voir le rapport de qualité des données.
  4. Explorer une matrice virtualisée, triable et filtrable.
  5. Passer de la matrice au graphe sans perdre la sélection.
  6. Enrichir les équipements.
  7. Comparer à une baseline.
  8. Générer un rapport et un bundle de preuve.

  Il faut également corriger plusieurs bugs concrets :

  - batchs de paquets potentiellement traités deux fois entre src/components/AnalyseView/BottomLong.vue:138 et src/store/capture.ts:114 ;
  - sélection native permettant d’importer deux fois le même fichier dans src/components/AnalyseView/panels/ImportPanel.vue:228 ;
  - import pouvant rester verrouillé si son nettoyage échoue ;
  - routes héritées vides ou cassées ;
  - erreurs de capture et d’export visibles seulement dans la console ;
  - export des logs présenté comme un fichier alors que le backend crée un répertoire.

  ### 4. Rendre le contrat frontend/backend fiable

  Les types TypeScript ne correspondent pas toujours aux événements Rust : champs imbriqués contre champs plats, graphData contre graph_data, puis utilisation de any dans le dispatcher. Le typecheck vert ne protège donc pas réellement le contrat,
  notamment dans src/store/capture.ts:149 et src/types/capture.ts:142.

  Je recommande :

  - génération automatique des bindings TypeScript depuis Rust ;
  - unions discriminées exhaustives ;
  - test de sérialisation Rust → JSON → TypeScript ;
  - versionnement du protocole IPC ;
  - erreurs structurées et affichées dans l’interface ;
  - rollback de l’interface lorsqu’une modification de label échoue.

  ### 5. Livrer des binaires reconnus comme sûrs par les OS

  La chaîne actuelle offre déjà build reproductible, SHA-256, provenance, Sigstore et SBOM. C’est très positif.

  Mais les bundles sont construits explicitement sans signature native dans .github/workflows/publish.yml:114. Sigstore ne remplace pas :

  - Developer ID, hardened runtime, notarisation et stapling macOS ;
  - Authenticode horodaté sous Windows ;
  - validation Gatekeeper et SmartScreen.

  Autre problème : une publication déclenchée par un tag peut contourner les quality gates de main, car .github/workflows/rust-ci.yml:3 ne s’exécute pas sur les tags.

  Une release pro doit obligatoirement :

  - reconstruire tous les tests/gates ;
  - vérifier que le commit taggé appartient à main protégé ;
  - utiliser un tag signé ;
  - scanner les artefacts avant publication ;
  - installer et lancer réellement chaque bundle ;
  - tester upgrade, rollback et désinstallation ;
  - supporter macOS Apple Silicon, pas uniquement x86_64.

  ### 6. Tester le produit réel, pas seulement ses fonctions

  Les contrôles locaux sont tous verts :

  - 39 tests frontend ;
  - 77 tests Tauri ;
  - 41 tests cœur/CLI ;
  - soit 157 tests réussis ;
  - build, typecheck, cargo fmt et Clippy strict réussis.

  C’est un excellent socle. Mais les parcours visibles ne sont pratiquement pas testés. Un ancien test de analyseView utilise encore Vue 2/Jest et n’est pas découvert par Deno.

  Il manque :

  - corpus versionné PCAP/PCAPNG multi-DLT et multi-interface ;
  - PCAP tronqués, malformés et hostiles ;
  - fuzzing/property tests du parseur ;
  - tests déterministes des courses arrêt/import ;
  - soak tests sur captures longues et forte cardinalité ;
  - E2E Tauri : import → matrice → graphe → labels → export ;
  - exécution réelle Windows, macOS et Linux ;
  - installation sur machine propre avec Npcap ;
  - tests d’accessibilité et de navigation clavier.

  ## Ce qui rendrait SONAR vraiment différenciant

  Une fois les P0 fermés, les fonctionnalités « Pro » les plus importantes sont déjà bien identifiées dans VISION.md:125 :

  - baseline et comparaison temporelle ;
  - inventaire d’actifs avec identité stable ;
  - détection d’équipements nouveaux, disparus ou modifiés ;
  - rapports PDF/HTML signés et reproductibles ;
  - format SFMS formellement spécifié, versionné et validable ;
  - exports JSON/API adaptés à l’automatisation ;
  - preuve testée du fonctionnement strictement passif ;
  - support bundle ZIP redigé, avec manifest technique ;
  - guide utilisateur, administrateur et dépannage ;
  - matrice OS/architecture et politique de support/EOL ;
  - SECURITY.md et canal privé de divulgation.

  Il faut aussi réduire les privilèges de la WebView : les capacités actuelles accordent notamment shell, process et des écritures filesystem assez larges dans src-tauri/capabilities/default.json:8. Idéalement, la capture privilégiée devrait être isolée
  dans un helper minimal ; l’interface complète ne devrait jamais tourner en root.

  ## Critères de sortie de bêta recommandés

  SONAR peut raisonnablement porter une étiquette « 1.0 Pro » lorsque :

  - chaque paquet est comptabilisé ou classé explicitement ;
  - aucun import/capture concurrent ne peut écraser des données ;
  - stop, limite de flux, crash et fermeture ne perdent rien silencieusement ;
  - les projets sont sauvegardables et récupérables ;
  - la matrice et le graphe forment un parcours terminé ;
  - les cinq parcours critiques passent en E2E sur chaque OS supporté ;
  - les installateurs sont signés, notarifiés et testés sur machines propres ;
  - les captures longues respectent des limites documentées de mémoire et de pertes ;
  - l’application démontre son absence d’émission réseau ;
  - aucun P0 n’est ouvert et chaque P1 restant est explicitement accepté ;
  - les rapports exportés contiennent provenance, qualité des données et signature.

  En résumé : le socle technique est bon, mais la priorité ne doit pas être d’ajouter beaucoup de fonctionnalités. Il faut d’abord rendre les résultats complets, explicables, persistants et testés de bout en bout. C’est ce passage de « ça fonctionne » à
  « je peux prouver pourquoi je fais confiance au résultat » qui fera réellement passer SONAR de bêta à produit professionnel. Aucun fichier n’a été modifié pendant cet audit.
