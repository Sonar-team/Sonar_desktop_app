• # Analyse complète de la code base

  Verdict général : la base est techniquement sérieuse, bien plus proche d’un produit actif que d’un prototype. Le cœur Rust est structuré, les tests locaux passent largement et le frontend possède déjà de bonnes protections de performance. En revanche,
  Sonar n’est pas encore prêt pour une exploitation longue durée ou une publication « audit-grade » : les principaux risques concernent la mémoire non bornée, les courses IPC, la fidélité des données et une chaîne de release qui donne parfois de fausses
  garanties.

  Aucun fichier n’a été modifié. Le worktree reste propre sur main.

  ## Périmètre audité

  J’ai couvert :

  - environ 238 fichiers applicatifs hors artefacts et dépendances ;
  - environ 7 900 lignes Vue/TypeScript/JavaScript ;
  - environ 10 600 lignes Rust internes ;
  - les configurations Tauri, Cargo, Deno et Vite ;
  - les workflows CI/CD, scripts de release, sécurité, SBOM et reproductibilité ;
  - les tests, la documentation et le packaging ;
  - les points d’intégration avec packet_parser.

  Le dépôt contient aussi près de 29 000 fichiers vendorés. Ils n’ont pas été relus ligne par ligne ; seuls leurs manifests, leur intégration et les zones ciblées du parser ont été audités.

  ## Architecture

  Le flux principal est cohérent :

  libpcap
    → thread de capture
    → canal Crossbeam borné
    → thread de traitement
    → packet_parser
    → FlowMatrix + GraphData
    → Channel Tauri
    → store Pinia
    → Sigma / Graphology / interface Vue

  L’initialisation Tauri et les commandes IPC sont centralisées dans src-tauri/src/lib.rs:81. Le pipeline est assemblé dans src-tauri/src/state/capture/capture_handle/mod.rs:55, puis traité dans src-tauri/src/state/capture/capture_handle/threads/
  processing.rs:529.

  Le frontend est organisé autour de Vue, Pinia, Sigma et Graphology. Le canal est distribué par src/store/capture.ts:22, puis consommé notamment par le graphe dans src/components/AnalyseView/NetworkGraphComponent.vue:95.

  Le workspace sonar-rust/Cargo.toml:1 constitue un second cœur Rust/CLI. Il n’est actuellement pas utilisé par l’application desktop, ce qui crée de la duplication et de la dérive.

  ## Points forts

  - Le canal capture → traitement est borné et la gestion de buffers évite une allocation systématique par paquet.
  - Les imports PCAP desktop propagent désormais les erreurs de fichier tronqué au lieu de produire silencieusement une matrice partielle.
  - La plupart des erreurs Rust sont typées.
  - Le code Rust interdit ou signale les unwrap/expect évitables.
  - TypeScript est configuré en mode strict.
  - Le frontend regroupe les événements graphe par frame et exécute ForceAtlas2 dans un worker.
  - La table de paquets live est bornée.
  - La CSP Tauri est restrictive et aucun v-html dangereux n’a été trouvé.
  - Les dépendances directes sont épinglées, Cargo est vendoré, les actions GitHub sont fixées par SHA et la release prévoit des attestations/Sigstore.
  - Aucun secret ou clé privée évident n’a été détecté.

  ## Risques critiques

  ### 1. Épuisement mémoire pendant une capture longue

  Le canal de paquets est borné, mais la matrice et le graphe ne le sont pas. Chaque nouveau tuple de flux, IP, arête ou MAC peut rester en mémoire jusqu’au reset. Un trafic à forte cardinalité ou des adresses aléatoires peuvent donc épuiser la RAM.

  Les limites autorisent jusqu’à un million de buffers et un snaplen de 262 144 octets dans src-tauri/src/state/capture/capture_config/mod.rs:13. Le produit théorique atteint environ 244 Gio de données en vol dans src-tauri/src/state/capture/
  capture_handle/mod.rs:89. L’allocation est paresseuse, mais aucun budget global en octets ne protège réellement le processus.

  À cela s’ajoutent :

  - FlowMatrix et GraphData sans politique d’éviction ;
  - la liste de MAC d’un nœud qui peut croître sans limite ;
  - les logs rotatifs configurés en conservation illimitée ;
  - un log par erreur de parsing, exploitable par du trafic volontairement malformé.

  Il faut introduire un budget mémoire global, une limite de cardinalité, une politique d’éviction/expiration et une rétention de logs bornée.

  ### 2. Release publique partielle ou non signée

  Le workflow crée la release publique avant la fin des builds dans .github/workflows/publish.yml:48. Les artefacts sont ensuite téléversés avant les hashes, attestations et signatures à partir de .github/workflows/publish.yml:144.

  Un échec en fin de workflow peut donc laisser publiquement une release incomplète ou non signée. La publication devrait être préparée en draft, vérifiée intégralement, puis rendue publique atomiquement.

  ### 3. Contrôle de reproductibilité non fiable

  Le script ne supprime pas réellement les artefacts Cargo entre les deux builds : security/repro-check.sh:30. Les deux passes réutilisent le même checkout et le même target, ce qui peut simplement comparer deux fois le même binaire.

  Les builds reproductibles doivent employer deux répertoires de travail et deux CARGO_TARGET_DIR indépendants, avec cache en lecture seule ou désactivé.

  ### 4. Installation privilégiée de Npcap insuffisamment maîtrisée

  Un EXE tiers est embarqué par src-tauri/tauri.conf.json:62 et lancé avec élévation administrateur par src-tauri/windows/hooks.nsh:17.

  Il manque :

  - une vérification CI d’un hash attendu ;
  - une validation Authenticode ;
  - une décision et une notice de licence Npcap ;
  - une validation réelle du hook NSIS, actuellement placé en préinstallation ;
  - un conditionnement de cette ressource au seul build Windows.

  C’est un bloqueur avant publication Windows publique.

  ## Risques élevés

  ### Cycle de démarrage et canal IPC

  Le backend envoie Started avant d’avoir trouvé/ouvert l’interface et appliqué le filtre dans src-tauri/src/state/capture/capture_handle/mod.rs:68. La commande mémorise également le canal avant que le démarrage ait réussi dans src-tauri/src/commandes/
  net_capture.rs:50. Un échec peut donc laisser un événement « démarré » suivi d’une erreur et un canal fantôme.

  Côté frontend, un double clic peut lancer deux appels simultanés dans src/components/NavBar/TopBar.vue:335. Le second canal remplace immédiatement le premier dans src/store/capture.ts:58, alors que le backend continue potentiellement à émettre sur
  l’ancien canal.

  Il faut une machine d’état explicite idle → starting → running → stopping, ainsi qu’un identifiant de session dans tous les événements.

  ### Contrat Rust/TypeScript désynchronisé

  Le type src/types/capture.ts:121 ne correspond plus au contrat réellement sérialisé :

  - mélange snake_case/camelCase ;
  - stopped déclaré deux fois ;
  - événements déclarés mais jamais dispatchés ;
  - champs graphe manquants ;
  - stats typées avec une structure différente de celle consommée.

  Le dispatcher utilise ensuite any, ce qui neutralise le mode strict. Le contrat devrait être généré depuis Rust ou partagé via un schéma versionné et testé par snapshots de sérialisation.

  ### Fidélité et auditabilité des données

  Plusieurs comportements empêchent de considérer les exports comme entièrement déterministes :

  - ordre aléatoire des HashMap dans l’export CSV de src-tauri/src/state/flow_matrix/mod.rs:273 ;
  - écriture directe dans le fichier final : une erreur disque peut laisser un fichier tronqué ;
  - mutex matrice conservé pendant l’I/O dans src-tauri/src/commandes/export/csv.rs:23 ;
  - dates avec perte des microsecondes et sans indication de fuseau ;
  - last_seen peut régresser lorsque plusieurs PCAP sont importés hors ordre chronologique ;
  - identifiants de tunnel fondés sur DefaultHasher, qui n’est pas un format persistant garanti ;
  - risque de formule CSV lorsque des labels commencent par =, +, - ou @.

  L’import de matrice est surtout structurel. Une IP invalide peut devenir None et une date invalide UNIX_EPOCH dans src-tauri/src/state/flow_matrix/mod.rs:565, au lieu de provoquer un rejet.

  Les exports devraient être triés, versionnés et écrits via fichier temporaire + fsync + renommage atomique.

  ### Parsing réseau

  Le parser suppose Ethernet et aucun contrôle du type de liaison libpcap n’a été trouvé. Un PCAP Linux cooked, radiotap ou autre DLT peut donc être interprété comme une trame Ethernet.

  La feature de mesure capture_timing change en plus le résultat fonctionnel : elle force inner: None dans src-tauri/vendor/packet_parser/src/parse/mod.rs:304, faisant disparaître les tunnels internes lorsque l’instrumentation est activée.

  Dans le second cœur, sonar-flows-core utilise while let Ok(packet) dans sonar-rust/crates/sonar-flows-core/src/pcap.rs:126. Toute erreur en milieu de fichier y est confondue avec une fin normale.

  ### Sémantique graphe et statistiques

  - Les arêtes sont agrégées par endpoints + protocole, mais conservent seulement les premiers ports observés : plusieurs services peuvent être présentés comme une seule connexion avec des ports trompeurs.
  - Les nœuds sont indexés par IP. Plusieurs MAC pour la même IP peuvent faire osciller le label, tandis que seule la première MAC est réellement éditable.
  - processed correspond au nombre de lignes/flux distincts, alors que l’interface l’affiche comme « Trames analysées ».
  - La déduplication des stats ignore justement les changements de processed.
  - L’arrêt envoie des stats à zéro, effaçant les derniers compteurs.
  - Le backend sérialise chaque paquet vers la WebView alors que l’interface n’en conserve que cinq.

  ### Labels

  L’import de labels comporte plusieurs pièges dans src-tauri/src/commandes/import/labels.rs:128 :

  - un chemin inexistant est lu comme un fichier vide et peut vider le store ;
  - une première ligne invalide peut être prise pour un header et ignorée ;
  - le fichier est relu trois fois ;
  - les MAC/IP valides mais non canoniques ne correspondent pas forcément aux valeurs normalisées du parser ;
  - l’arbitrage frontend applique les changements séquentiellement sans transaction.

  ## CI, sécurité et supply-chain

  Les contrôles locaux sont meilleurs que les contrôles réellement imposés aux PR :

  - .github/workflows/rust-clippy.yml:47 lance Cargo depuis une racine sans Cargo.toml et masque l’échec avec continue-on-error.
  - Aucun workflow principal n’exécute les 37 tests Deno ni le typecheck frontend.
  - sonar-rust n’est pas couvert par le workflow Rust principal.
  - Le formatage Rust échoue actuellement localement.
  - Les tests Deno utilisent --no-check et sont exclus de vue-tsc.
  - Le SBOM frontend généré par script/ci/generate-sbom-artifacts.sh:46 ne contient pas Vue, Vite, Pinia ou Sigma. Les SBOM suivis décrivent encore la version 4.2.0 au lieu de 4.3.1.
  - cargo-vet n’apporte actuellement aucune garantie réelle : audits vides, aucune source importée et plusieurs centaines d’exemptions.
  - La licence est incohérente : le texte indique AGPL v3 ou ultérieure, tandis que les manifests déclarent AGPL-3.0-only.
  - Les permissions Tauri de src-tauri/capabilities/default.json:8 incluent des capacités shell/process/filesystem inutilisées ou dupliquées.
  - La stack Loki/Grafana de développement écoute largement avec Loki sans authentification et admin/admin.
  - .env* et .secrets.act devraient être ajoutés aux exclusions Git/Docker.

  ## Frontend et UX

  Les principaux défauts frontend sont :

  - course entre snapshot complet et anciens graphBatch encore en file ;
  - journal de paquets alimenté à la fois par les événements unitaires et batch dans src/components/AnalyseView/BottomLong.vue:138 ;
  - édition de label optimiste sans rollback ;
  - annulation de sauvegarde des logs transformée en rejet non géré ;
  - filtre BPF validant des adresses comme 999.999.999.999 ou des CIDR /99 ;
  - route /readPcap toujours exposée mais cassée dans src/views/readPcapView.vue:31 ;
  - ForceAtlas2 actif indéfiniment ;
  - recalculs coûteux des arêtes et absence de virtualisation des grosses listes ;
  - dépendances vraisemblablement inutilisées : Chart.js, html2canvas, color-convert et plusieurs plugins Tauri ;
  - accessibilité insuffisante : boutons icônes sans nom accessible, dialogues sans sémantique/focus trap, formulaires mal associés, graphe utilisable uniquement à la souris ;
  - titre, favicon et lang="en" provenant encore du scaffold Vite.

  ## Mode headless et duplication

  Le mode headless reste incomplet :

  - il utilise encore le pipeline pensé pour la WebView et un canal factice ;
  - aucun export automatique n’est effectué à l’arrêt ;
  - les labels initiaux ne sont pas chargés comme dans le mode GUI ;
  - aucune gestion robuste des signaux de service n’est visible ;
  - les données restent seulement en mémoire.

  Le workspace sonar-rust duplique par ailleurs une grande partie de FlowMatrix sans être consommé par l’application. Il faut choisir un seul cœur canonique et faire dépendre le desktop et le CLI de cette crate.

  ## Plan de remédiation recommandé

  1. Bloquer les releases publiques et corriger publication atomique, reproductibilité, Npcap et licence.
  2. Ajouter des limites mémoire globales, de cardinalité, de durée et de rétention des logs.
  3. Introduire la machine d’état de capture et un identifiant de session IPC.
  4. Générer un contrat IPC partagé et ajouter des tests de sérialisation Rust ↔ TypeScript.
  5. Rendre imports/exports stricts, déterministes et atomiques.
  6. Vérifier le DLT et garantir que les features d’instrumentation ne modifient jamais les données.
  7. Réparer les gates CI : fmt, clippy, tests/typecheck Deno, deux workspaces Rust, SBOM validé.
  8. Fusionner le cœur desktop et sonar-flows-core.
  9. Ajouter des tests E2E capture/import/export, des PCAP versionnés, du fuzzing parser et des tests de charge.
  10. Supprimer les routes et composants legacy, puis traiter performance et accessibilité.

  En l’état, je qualifierais Sonar de bonne base bêta avec un cœur localement sain, mais pas encore de produit publiable avec des garanties fortes de disponibilité, de reproductibilité et d’intégrité des données.
