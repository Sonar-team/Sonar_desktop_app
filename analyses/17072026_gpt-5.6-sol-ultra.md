 # Analyse complète

  Verdict : SONAR 4.7.0 est une bêta avancée avec une architecture Rust sérieuse, une capture bien pensée et une excellente base supply-chain. En revanche, l’application n’est pas encore prête pour un usage « audit-grade » ou une publication professionnelle sans réserve. Les principaux obstacles sont la persistance des sessions, la fidélité du graphe, quelques défauts de concurrence et de validation, l’absence de matrice dans le parcours principal et des gates de release incomplètes.

  Analyse réalisée sur main, commit 9e5a2540. Le dépôt est resté propre et aucun fichier n’a été modifié.

  ## Cartographie

  Le code propriétaire représente environ 26 000 lignes :

  - Frontend Vue/TypeScript : 10 038 lignes, 76 fichiers.
  - Backend Tauri : 10 636 lignes Rust, 48 fichiers.
  - Cœur et CLI : 5 330 lignes Rust, 10 fichiers.
  - 28 362 fichiers suivis, dont 27 921 fichiers de crates vendored, soit environ 956 Mio.

  L’architecture principale est la suivante :

  Vue 3 / Pinia / Sigma
            ↕ IPC Tauri typé + Channel
  Commandes Tauri et machine d’état
            ↓
  libpcap → canal borné → thread de traitement
                             ↓
                  FlowMatrix + GraphData
                             ↓
               événements batchés vers Vue

  sonar-cli ─────────→ sonar-flows-core
  desktop  ──────────→ sonar-flows-core 0.3.0 publié

  L’initialisation des plugins, des six états partagés et des commandes IPC est centralisée dans src-tauri/src/lib.rs:74. Le pipeline de capture utilise correctement un canal borné, un pool de buffers et deux threads dans src-tauri/src/state/capture/capture_handle/mod.rs:57. Le contrat événementiel est versionné et structuré dans src-tauri/src/events/mod.rs:35.

  ## Points forts

  - La capture possède une machine d’état, des identifiants de session et un filtrage des événements périmés côté frontend.
  - Le canal de paquets est borné, la mémoire des buffers est budgétée et la capture live s’arrête à 250 000 flux.
  - Les paquets, statistiques et mises à jour du graphe sont batchés ; ForceAtlas2 s’exécute dans un worker.
  - Les imports PCAP sont transactionnels : matrice et graphe sont construits localement puis substitués uniquement après succès dans src-tauri/src/commandes/import/pcap.rs:537.
  - Les DLT non supportés et les mélanges de DLT sont explicitement refusés.
  - Le contrat IPC TypeScript est généré depuis Rust et contrôlé en CI.
  - Le cœur métier est extrait dans sonar-flows-core, réutilisé par le CLI.
  - Aucun client réseau applicatif explicite n’a été trouvé. La CSP limite les connexions à l’IPC dans src-tauri/tauri.conf.json:12.
  - Les dépendances directes sont épinglées, Cargo est vendored, les actions GitHub sont fixées par SHA et les releases disposent de hashes, attestations et signatures Sigstore.
  - VISION.md:25 est particulièrement clair sur la passivité, l’interopérabilité SFMS et la séparation desktop/CLI.

  ## Problèmes bloquants

  ### P0 — Sessions non persistantes

  La matrice, le graphe et les labels utilisateur vivent uniquement en mémoire. Seule la configuration de capture est persistée. La fermeture confirmée appelle directement exit(0) dans src/utils/appExit.ts:19, sans autosave, état « modifié », arrêt coordonné ou récupération après crash.

  Conséquence : une capture ou un travail de labellisation non exporté est perdu à la fermeture ou au crash. Pour un outil d’audit, c’est le premier blocage produit. La roadmap le reconnaît déjà comme P0 dans Roadmap.md:33.

  ### P0 — Identité d’actif incorrecte dans le graphe

  Le graphe indexe ses nœuds uniquement par IP, ou par MAC en repli, dans sonar-rust/crates/sonar-flows-core/src/graph.rs:13. Deux équipements ayant la même IP sur des VLAN, sites ou interfaces d’observation différents sont fusionnés. Les MAC supplémentaires deviennent des anomalies du même nœud.

  La matrice conserve davantage de contexte, mais le graphe peut présenter une topologie trompeuse. Il faut définir une identité telle que (site, capteur, interface, VLAN, IP/MAC) avant de bâtir les fonctions de baseline ou de comparaison.

  ### P0 — La matrice n’existe pas dans le parcours actif

  La vue principale rend uniquement le graphe et les cinq dernières trames dans src/views/analyseView.vue:31. Matrice.vue et homeView.vue sont inaccessibles, bien que des états et événements de bascule subsistent.

  La route /readPcap est également cassée : vue vide, JSON.parse non protégé et mauvais contrat IPC dans src/views/readPcapView.vue:31. Le produit promet donc « capture → matrice → graphe », mais son parcours principal ne livre que le graphe.

  ### P0/P1 — Concurrence et effacement accidentel

  Un interblocage est possible lors d’appels concurrents à démarrage/arrêt :

  1. start_capture verrouille la matrice puis attend CaptureState.
  2. stop_capture conserve CaptureState pendant le join() des threads.
  3. Le thread rejoint peut attendre la matrice.

  Les verrous concernés sont visibles dans src-tauri/src/commandes/net_capture.rs:39 et src-tauri/src/state/capture/capture_handle/threads/processing.rs:227.

  Autre défaut : convert_from_pcap_list([]) produit une matrice et un graphe vides puis remplace les données existantes dans src-tauri/src/commandes/import/pcap.rs:501. L’UI actuelle bloque normalement ce cas, mais le backend doit protéger son propre contrat IPC.

  ### P0 — Release non suffisamment qualifiée

  Le CI principal exécute tests, Clippy, audit, deny et contrôles frontend, mais seulement sur les push/PR vers main dans .github/workflows/rust-ci.yml:3. Le workflow de publication déclenché par tag ne dépend pas de ces gates dans .github/workflows/publish.yml:3.

  Autres écarts :

  - aucune vérification tag == package.json == Cargo.toml == tauri.conf.json ;
  - le binaire brut est construit et testé, puis les bundles sont reconstruits séparément sans preuve qu’ils contiennent exactement ce binaire ;
  - les jobs de build possèdent directement contents: write, OIDC et les droits d’attestation ;
  - aucune signature native Authenticode, Developer ID ou notarisation Apple ;
  - macOS est limité à x86_64-apple-darwin dans config/build-versions.env:19 ;
  - pas de vrai test d’installation et de démarrage sur machine propre ;
  - un rerun sur une release déjà publique peut remplacer progressivement les artefacts avec --clobber.

  La création initiale en draft et la publication finale atomique sont néanmoins de très bons acquis.

  ## Intégrité métier et exports

  Plusieurs défauts concrets restent à corriger :

  - GraphData::refresh_labels conserve l’ancien label lorsque le résolveur renvoie None. Un label supprimé du store peut donc rester visible dans le graphe : sonar-rust/crates/sonar-flows-core/src/graph.rs:526.
  - La validation SFMS ne contrôle pas encap_id. Les compteurs invalides deviennent zéro, les identifiants hexadécimaux invalides sont ignorés et un tunnel peut déclarer plus de paquets que la ligne : sonar-rust/crates/sonar-flows-core/src/matrix.rs:77.
  - Plusieurs additions de compteurs ne sont pas contrôlées : panic en debug ou wrap en release sur des données forgées.
  - L’échappement contre les formules CSV protège les labels, mais pas origin, qui peut provenir d’un nom de fichier hostile : sonar-rust/crates/sonar-flows-core/src/matrix.rs:399.
  - L’export atomique utilise un temporaire prévisible <destination>.tmp et rename, avec risques de collision et de remplacement non portable sous Windows : sonar-rust/crates/sonar-flows-core/src/matrix.rs:652.
  - La version du préambule SFMS est lue mais sa compatibilité n’est pas réellement contrôlée.

  ## Frontend et UX

  Les défauts les plus importants sont :

  - displayCaptureError lance lui-même un TypeError si l’erreur est null, undefined ou une chaîne : src/errors/capture.ts:29.
  - Le nettoyage des imports place des await avant la remise à zéro de isConverting. Une erreur secondaire peut laisser le panneau en état occupé : src/components/AnalyseView/panels/ImportPanel.vue:318.
  - Effacer le badge de filtre pendant une capture rend l’UI mensongère : le backend ne modifie que le filtre du prochain démarrage, dans src-tauri/src/commandes/net_capture.rs:154.
  - L’édition d’un label est optimiste sans rollback en cas d’échec IPC : src/components/AnalyseView/NetworkGraphComponent.vue:457.
  - Un événement started d’import de labels efface le badge DLT existant dans src/store/capture.ts:130.
  - La validation BPF accepte notamment des IP impossibles, des CIDR /99 et des plages inversées.
  - Le graphe est essentiellement utilisable à la souris. Les modales, associations label/champ, focus clavier et contrastes ne satisfont pas encore WCAG 2.2 AA.
  - ImportPanel.vue, NetworkGraphComponent.vue, labels.rs et matrix.rs sont devenus de gros points chauds de 800 à 1 500 lignes.

  ## Sécurité runtime

  La posture hors ligne et la CSP sont bonnes, mais les capabilities Tauri accordent à la fenêtre principale shell:default, process:default, fs:default et l’écriture récursive dans tout $HOME, Documents, Bureau et Téléchargements : src-tauri/capabilities/default.json:8.

  Le frontend n’utilise pas le shell. Les permissions devraient être réduites à :

  - process:allow-exit ;
  - dialogue et logs strictement nécessaires ;
  - accès fichier accordé dynamiquement après sélection ;
  - validation backend des chemins fournis aux commandes Rust.

  Les logs exposent hostname, chemins de travail et exécutable dans src-tauri/src/setup/mod.rs:14, ainsi que les interfaces, IP/MAC et parfois toute la table des labels. Une politique de redaction est nécessaire avant tout export de support.

  ## Tests et couverture

  Contrôles locaux réussis :

  - Frontend : lint, format, vue-tsc, build Vite.
  - Tests frontend : 39/39.
  - Backend Tauri : 117 tests, documentation réussie avec un test ignoré.
  - Cœur et CLI : 69 tests.
  - Clippy strict -D warnings et Rustfmt : réussis sur les deux workspaces.
  - Bundle frontend : 444,02 kB, 131,14 kB gzip.

  Limites :

  - aucun test WebView/Tauri E2E ;
  - aucun test d’installateur réel ;
  - aucune validation Windows/macOS locale ;
  - très peu de tests de composants ou d’erreurs asynchrones ;
  - pas de test de concurrence reproduisant le cycle start/stop ;
  - le workflow de couverture ne lance que src/tests/*.test.js, soit 3 tests au lieu des 39 actuels : .github/workflows/covecode.yml:83 ;
  - analyseView.spec.js est un ancien test Jest/Vue 2 non exécuté ;
  - sonar-rust est absent des sources SonarQube : sonar-project.properties:6.

  cargo audit, cargo deny et cargo-vet n’ont pas été recalculés localement, les outils n’étant pas installés. Le CI prévoit audit/deny, mais cargo-vet ne fournit actuellement aucune assurance : pas d’audits, beaucoup d’exemptions et aucune gate.

  ## Performance

  La capture live est plutôt bien protégée : canal borné, pool de buffers, batches, télémétrie de backpressure, plafond de flux et drainage lors de l’arrêt.

  Les imports restent le principal risque :

  - chaque PCAP est parcouru une fois pour compter, puis une seconde fois pour traiter : src-tauri/src/commandes/import/pcap.rs:369 ;
  - aucun plafond de fichiers, lignes, nœuds ou flux ;
  - matrice et graphe complets sont conservés simultanément avant le swap ;
  - aucun mécanisme d’annulation ;
  - le chargement d’un snapshot graphe reste synchrone sur le thread UI.

  ## Supply-chain, dépôt et documentation

  La base supply-chain est meilleure que celle de la plupart des projets de cette taille, mais certains artefacts donnent une fausse impression d’actualité :

  - source-manifest.sha256 est fortement périmé. Vérification locale : 27 775 entrées valides, 241 hashes modifiés, 1 569 fichiers disparus et 333 fichiers actuels absents. Aucun workflow n’exécute son générateur security/generate_manifest.sh:9.
  - Les SBOM génériques indiquent frontend 4.3.1 et backend 4.2.0 pour une application 4.7.0. Le backend divulgue également un ancien chemin local : sbom/sonar-backend.cdx.json:21.
  - Les SBOM backend ne représentent que la cible Linux x86_64.
  - LICENSE.md:1 contient un avis AGPL mais pas le texte complet de la licence ; les notices des dépendances ne sont pas générées et embarquées.
  - Un fichier de télémétrie de 48 Mio et 146 837 lignes est suivi par Git : observability/data/sonar-logs/sonar-timing.jsonl:1. Il devrait être remplacé par un petit fixture synthétique.
  - La vision et la roadmap sont très bonnes, mais la roadmap annonce encore 4.4.0 alors que le code est en 4.7.0.
  - CONTRIBUTING.md ne documente pas l’installation, les commandes Deno/Rust, l’architecture ou les règles de test.
  - Le desktop dépend de sonar-flows-core = 0.3.0 publié, pas directement de la copie locale : src-tauri/Cargo.toml:46. Les sources locales et vendored sont identiques aujourd’hui, mais aucune gate ne garantit qu’elles le resteront.

  ## Feuille de route recommandée

  1. Avant tout nouveau développement fonctionnel :
      - corriger le deadlock start/stop ;
      - rejeter les imports PCAP vides ;
      - corriger la suppression de labels ;
      - valider strictement encap_id et utiliser des additions contrôlées ;
      - sécuriser l’export CSV et son temporaire ;
      - réparer les états d’erreur frontend et supprimer /readPcap.

  2. Pour fermer la bêta :
      - introduire projets persistants, autosave atomique et récupération après crash ;
      - définir l’identité d’actif contextualisée ;
      - réintégrer une matrice virtualisée et testée dans la vue principale ;
      - ajouter des E2E capture/import/matrice/graphe/labels/export ;
      - réduire les capabilities et redacter les logs.

  3. Avant la prochaine release professionnelle :
      - faire dépendre la release de toutes les gates qualité et sécurité ;
      - vérifier l’alignement tag/versions ;
      - séparer build sans privilège et publication/signature ;
      - prouver que le binaire testé est celui des installateurs ;
      - ajouter Authenticode, Developer ID, notarisation et Apple Silicon ;
      - régénérer et contrôler manifestes, SBOM et notices de licences.

  En résumé : le socle technique est bon et plusieurs décisions sont déjà de niveau professionnel. Le travail restant concerne moins une réécriture qu’une fermeture rigoureuse des garanties : conservation des sessions, identité correcte des actifs, cohérence matrice/graphe, défense des frontières IPC et preuve que l’artefact publié est exactement celui testé.
